# Food and Training App — CLAUDE.md

Personal, single-user Android web app (installable PWA) for strength training, body
measurements and daily macros. `SCOPE.md` is the agreed V1 scope and wins over this file
if they disagree. Do not build anything listed under "Out of scope for V1".

## Hard constraints

- **Zero running cost.** No paid hosting, no paid APIs, no AI calls, no backend, no accounts.
- **Phone-only data.** Everything lives in IndexedDB on the phone. No network calls for data.
- **Offline-first.** The app must fully work with no connection (gym). Service worker
  precaches the whole app shell.
- **Free static hosting.** The build output is plain static files (GitHub Pages).
- **Metric only.** kg for body/lifted weight, cm for lengths, g for food. No unit conversion.
- **Backup = export/import.** Full JSON export and restore are V1 features, not extras.
- **Minimal dependencies.** Add a runtime dependency only if it removes real work and is small.
  Ask before adding one.
- **Target device:** Android Chrome, portrait phone. Design mobile-first, large tap targets.

## Stack

Runtime dependencies: `preact`, `idb`. Nothing else without asking.

### Commands

Node 24 LTS is installed per-user at `~/.local/node` (on PATH via `~/.zshrc`; non-login
shells need `export PATH="$HOME/.local/node/bin:$PATH"`). Icons are generated by
`npm run icons` (`scripts/make-icons.mjs`, no dependencies).

- `npm run dev` — local dev server
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build (test the service worker here)
- `npm test` — Vitest (runs with `TZ=Europe/Berlin` so DST cases are deterministic)

### Code layout

```
src/
  db/          types.ts (record shapes), schema.ts (stores, indexes, migrations, getDB),
               persist.ts, status.ts, id.ts, one repo file per area
               (exercises.ts, routines.ts, workouts.ts, measurements.ts, macros.ts, foods.ts),
               backup.ts (export/import)
  domain/      pure functions: dates.ts (local YYYY-MM-DD, Monday = 0), target-for-date, day-type-for-date, macro scaling, totals
  ui/          screens/ and components/
  router.ts
  main.tsx
```

UI never talks to IndexedDB directly — it calls the repo functions in `src/db/`.
Pure logic goes in `src/domain/` and gets unit tests.

## Data conventions

- **IDs:** `crypto.randomUUID()` strings.
- **Calendar days:** local date string `YYYY-MM-DD` (field name `date`). Never derive a day
  from a UTC timestamp.
- **Instants:** epoch milliseconds (`number`), field names ending in `At`.
- **Numbers:** kg and cm as decimals; food grams and macros as decimals, rounded only for display.
- **Soft delete only where the scope says "archive"** (exercises, measurement types, foods).
  Everything else is a real delete.
- **Snapshots over joins for history.** Logged data copies whatever it needs so later edits to
  library items never rewrite the past.
- Every schema change bumps the DB version with an explicit migration in `schema.ts`, and the
  export format carries `schemaVersion`.

## Data model (IndexedDB object stores)

### Training

**`exercises`** — the exercise library
- `id`, `name`, `archived: boolean`, `createdAt`
- Index: `name`. Archived exercises are hidden from pickers but keep all history.

**`routines`** — saved templates
- `id`, `name`, `exerciseIds: string[]` (ordered), `createdAt`, `updatedAt`
- Duplicate = copy with new id and name "… (copy)". Deleting a routine does not touch workouts.

**`workouts`** — one session
- `id`, `date`, `startedAt`, `endedAt: number | null`, `durationSec: number | null`
- `routineId: string | null`, `routineName: string | null` (snapshot; null = free workout)
- `exercises: { id, exerciseId, order }[]` — the session's own exercise list, copied from the
  routine at start. Add/remove/swap edits this list only, never the routine.
- Indexes: `date`, `startedAt`, `endedAt` (rows with `endedAt: null` are left out of that
  index by IndexedDB, so it lists finished workouts only).
- An in-progress workout has `endedAt === null`; at most one at a time. The timer is
  computed from `startedAt`, so it survives the app being closed or the phone restarting.

**`sets`** — every set, kept for later analysis
- `id`, `workoutId`, `workoutExerciseId`, `exerciseId`, `date` (copied from workout),
  `order`, `reps`, `weightKg`, `createdAt`
- Indexes: `workoutId`, `[exerciseId, date]`.
- "Previous values": the most recent *other* finished workout containing that exercise,
  via `[exerciseId, date]` descending, then its sets in `order`.
- Swapping an exercise in a session updates `exerciseId` on that slot and its sets.
- Removing an exercise from a session deletes its sets (confirm in UI if sets exist).
- Each exercise appears at most once per workout (and per routine). Starting from a routine
  skips exercises that are archived.
- An in-progress workout can be discarded (deletes it and its sets, after a confirm).
- A finished workout's date, start and end can be corrected from History (e.g. Finish tapped
  late); this also moves its sets to the new date. Max 24 h; an end before the start means
  past midnight.
- Weights accept a comma or a dot as decimal separator (phone keyboards); 0 kg = bodyweight.
  Reps are whole numbers 1-999.

### Body measurements

**`measurementTypes`**
- `id`, `name`, `unit: 'kg' | 'cm'`, `archived: boolean`, `isDefault: boolean`, `createdAt`
- Seeded on first run with one row: Body weight, `kg`, `isDefault: true`.

**`measurementEntries`**
- `id`, `typeId`, `date`, `value`, `createdAt`
- Indexes: `[typeId, date]`, `date`.
- A multi-type entry in the UI writes one row per type with the same `date`.
- One value per type per day: logging a type again on the same date replaces that value, and
  moving an entry onto a date that already has one is refused. Values must be > 0 (max 500 kg /
  300 cm). A type's unit is fixed at creation.

### Macro goals

Targets and the weekly schedule are **versioned by effective date**, so changing them never
rewrites past days and history is derived, not copied per day.

**`macroTargets`**
- `id`, `dayType: 'workout' | 'rest'`, `effectiveFrom` (date), `kcal`, `proteinG`, `carbsG`, `fatG`
- Index: `[dayType, effectiveFrom]`.
- Target for a day = row with that day's type and the latest `effectiveFrom <= date`.
- Editing a target writes a new row effective today (or updates today's row if one exists).

**`scheduleVersions`**
- `id`, `effectiveFrom` (date), `workoutWeekdays: number[]` (0 = Monday … 6 = Sunday)
- Index: `effectiveFrom`. Same "latest version on or before the date" rule.

**`dayOverrides`**
- key `date`, `dayType: 'workout' | 'rest'`
- Day type for a date = override if present, else the schedule version in force that day.

### Food

**`foods`** — personal food list
- `id`, `name`, `basis: 'per100g' | 'perServing'`, `servingLabel: string | null`
  (e.g. "1 bar"), `kcal`, `proteinG`, `carbsG`, `fatG` (per basis unit),
  `favourite: boolean`, `archived: boolean`, `lastUsedAt: number | null`, `createdAt`
- Indexes: `name`, `lastUsedAt`. (IndexedDB cannot index booleans, so favourites are a
  filter over the food list, which stays small.)

**`foodEntries`** — what was eaten
- `id`, `date`, `foodId: string | null`, `name` (snapshot), `amount`,
  `amountUnit: 'g' | 'serving'`, `kcal`, `proteinG`, `carbsG`, `fatG` (totals for this
  entry, snapshot), `loggedAt`
- Indexes: `date`, `foodId`.
- Logging a saved food: user enters amount; totals are computed from the food and stored.
- Manual entry: user enters name, amount and the totals for that amount; the entry is stored
  as-is and a `foods` row is created by normalising to the chosen basis (grams → per 100 g;
  servings → per serving).
- Recent = `foods` by `lastUsedAt` descending; favourites = `favourite === true`.
- Editing a saved food does not change past entries.

### App

**`meta`** — key/value
- `schemaVersion`, `lastExportAt`, `seededAt`

## Export / import

- Export: one JSON file `food-training-backup-YYYY-MM-DD.json`:
  `{ app: "food-training", schemaVersion, exportedAt, stores: { <storeName>: rows[] } }`.
  Delivered via the Web Share API with a file when available, otherwise a download link.
- Import: validate `app` and `schemaVersion` (run migrations for older versions), show counts,
  confirm, then replace all stores in a single transaction. Never merge.
- A failed restore leaves the existing data untouched (one transaction). Old backups missing
  stores added later are filled with empty lists; add a backup migration in `backup.ts` with
  every schema change that alters record shapes.
- Train shows a reminder when there is training data and no backup in the last 7 days.
- Request `navigator.storage.persist()` on first run to reduce the risk of the browser
  evicting data. Show the date of the last export in Settings.

## Build order

Follow this order. Finish and verify each step on the phone before starting the next.

1. **Scaffold** — Vite + Preact + TS, hash router, app shell with bottom nav, PWA manifest +
   service worker, GitHub Pages deploy workflow. Install to home screen and confirm offline load.
2. **Data layer** — `schema.ts` with all stores and indexes above, seed body weight,
   `storage.persist()`, Vitest + fake-indexeddb set up.
3. **Exercise library** — add, rename, archive/unarchive.
4. **Routines** — create, edit, reorder, duplicate, delete.
5. **Workout session** — start from routine or empty; add/remove/swap exercises; add/edit/
   delete sets; previous values; running timer; finish (stores end time and duration);
   resume an unfinished workout on app open.
6. **Workout history** — list of past workouts; open and edit any of them.
7. **Export / import** — generic over all stores, so real training data is backed up early.
8. **Body measurements** — types (add, rename, archive), single and multi-type entry,
   per-type history with edit and delete.
9. **Macro goals** — the two target sets, weekly schedule, per-day override, target lookup
   for any date (unit-tested).
10. **Food logging** — food list, manual entry, log saved food by amount, recent and
    favourites, edit/delete entries on any day, daily view (consumed / target / remaining).
11. **Polish** — empty states, confirm dialogs for deletes, final offline and install check.

## Working rules

- Keep it small and boring. No state library, no CSS framework, no component library.
- Check `SCOPE.md` before adding anything not explicitly listed; ask rather than expand scope.
- Graphs are out of scope, but every record must keep the fields listed above so they are
  possible later.
